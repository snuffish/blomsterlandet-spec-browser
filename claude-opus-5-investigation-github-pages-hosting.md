# Investigation: Hosting the Växtregister on GitHub Pages

**Goal:** Determine whether this Vite + React spec-browser can be hosted on GitHub Pages, and what would have to change for it to work.
**Scope:** Whole workspace `/Users/snuffish/Projects/blomsterlandet` — build config, data-loading layer, URL-state layer, dev-only server middleware, and the `harvest/` pipeline that produces the dataset.
**Status:** Complete — technically feasible with two mandatory changes. Two non-technical decisions await the user (§9).
**Date:** 2026-09-23

---

## 1. Questions Answered

1. **Is the production build actually static — does anything need a server at runtime?**
   → **Yes, fully static.** The only server-side code is the `/__harvest` middleware, registered with `apply: 'serve'` (`vite.config.ts:29`), so Vite never includes it in a `vite build`. The one UI element that calls it is gated behind `import.meta.env.DEV` (`src/App.tsx:54`) and is tree-shaken out of the production bundle. No API, no SSR, no runtime Node.

2. **Will the compiled asset URLs survive being served from a repository sub-path?**
   → **No — this is blocker #1.** `vite.config.ts:66-79` defines no `base` option, so Vite falls back to its default `'/'` and emits `<script src="/assets/index-*.js">`. The remote is `git@github.com:snuffish/blomsterlandet-spec-browser.git`, so the project-page URL is `https://snuffish.github.io/blomsterlandet-spec-browser/` — every absolute `/assets/*` request would resolve to `snuffish.github.io/assets/*` and 404.

3. **Will the dataset fetches survive the sub-path?**
   → **Yes, already correct.** `src/hooks/useDataset.ts:23-25` fetches `'data/products.json'`, `'data/facets.json'`, `'data/meta.json'` — **relative, no leading slash**. Under `/blomsterlandet-spec-browser/` these resolve to `/blomsterlandet-spec-browser/data/*.json`. GitHub Pages 301-redirects a bare `/repo` to `/repo/`, so the trailing-slash base is reliable. No change needed here.

4. **Does the dataset itself reach GitHub?**
   → **No — this is blocker #2.** `.gitignore:5` ignores `public/data/`, and `git ls-files public/` returns nothing. The 3.5 MB `products.json` that the whole app depends on is untracked. A Pages deploy from the repo as it stands would publish a shell that renders the "Datasetet saknas" error branch (`src/App.tsx:36`).

5. **Does the app use client-side path routing, which would need a `404.html` SPA fallback?**
   → **No.** All view state lives in the `?k=` query string: `src/hooks/useChain.ts:19-21` writes `` `${window.location.pathname}?k=${query}` `` via `history.replaceState`, preserving whatever path prefix it was served from. `src/lib/chain-url.ts:14-38` encodes/decodes that single param. The selected-product detail view is React state (`src/App.tsx:17`), not a route. **One HTML entry point, no deep paths — the standard SPA 404 workaround is unnecessary.**

6. **Is the payload within GitHub Pages limits?**
   → **Comfortably.** Measured: `products.json` 3 479 517 B raw / **379 729 B gzipped**; `facets.json` 24 460 / 4 923; `meta.json` 1 121 / 450. Total site well under the 1 GB published-site limit and the 100 MB per-file Git limit. Pages gzips `application/json`, so the over-the-wire cost is ~385 KB.

7. **Do product images add weight or break off-origin?**
   → **Neither.** Images are hotlinked to the source CDN — `src/components/ProductCard.tsx:19` renders `thumbnail(product.image)`, and `src/lib/format.ts:12-13` only appends `?width=320&format=webp&quality=80` to an absolute `https://www.blomsterlandet.se/globalassets/...` URL (verified against `public/data/products.json`). Zero local image bytes; `src/index.css` contains no `url()`, `@import`, or `@font-face` references at all.

---

## 2. Executive Summary (TL;DR)

- **Yes — this app is a natural fit for GitHub Pages.** It is a single-entry, query-string-only static SPA with no production server dependency, no deep routing, and a ~385 KB gzipped data payload.
- **Exactly two things block it today:** (a) `vite.config.ts` has no `base`, so asset URLs break under the `/blomsterlandet-spec-browser/` sub-path; (b) `public/data/` is gitignored, so the dataset never reaches GitHub.
- **The data-loading layer is already sub-path-safe** — relative fetch paths (`useDataset.ts:23-25`) and pathname-preserving history writes (`useChain.ts:20`) — which removes the usual source of Pages breakage.
- **The real decision is not technical but editorial:** whether the dataset is committed as a snapshot or regenerated by a scheduled Actions harvest, and whether a scraped third-party catalogue should be published at a public URL at all (§9).

### 3.1 The data-production side

`harvest/build.ts:13` writes its output to `<root>/public/data`. The pipeline fetches from `https://www.blomsterlandet.se` (`harvest/http.ts:9`) at concurrency 5 (`harvest/http.ts:17`) with a self-identifying User-Agent (`harvest/http.ts:12-14`) and retry/backoff on 408/425/429/5xx (`harvest/http.ts:19`). Responses are cached to `harvest/cache/` (`harvest/http.ts:8`, `:22-23`) — **767 MB across 1 825 HTML files locally**, gitignored at `.gitignore:3` and which must stay that way.

The prior investigation recorded a full cold harvest at **~3.6 minutes for 1 740 PDPs** with 0 errors, and that `robots.txt` disallows only `/episerver/` and `/utils/` (`claude-opus-5-investigation-blomsterlandet-product-index.md:29`). That figure is what makes a CI-side harvest viable at all.

## 6. Blast Radius

- **Files a Pages setup would touch:** `vite.config.ts` (add `base`), `.gitignore` (only under Option A), plus a new `.github/workflows/*.yml`. No application source needs to change.
- **Nothing in `src/` depends on the dev endpoint** beyond the two DEV-gated modules (`src/hooks/useHarvest.ts`, `src/components/HarvestButton.tsx`), so a production deploy cannot regress the filter/sort behaviour.
- **Existing test coverage:** `src/App.test.tsx`, `src/lib/chain.test.ts`, `src/lib/query.test.ts`, `harvest/normalize.test.ts`, run via `vitest run` (`package.json:12`). **No test asserts anything about `base`, asset URL resolution, or deployment** — a `base` regression would not be caught by the suite.
- **Repo weight:** currently `size-pack: 0 bytes`. Committing the dataset adds ~3.5 MB per snapshot; because `products.json` is a single large text blob, each re-harvest commit stores a fresh delta and the repo grows over time if the data is committed on a schedule.

## 7. Options & Trade-offs

### Option A: Commit the dataset, build-and-deploy on push (Recommended)
- **Concept:** Un-ignore `public/data/`, commit the three JSON files as a snapshot, and add a GitHub Actions workflow that runs `npm ci && npm run build` and publishes `dist/` via `actions/upload-pages-artifact` + `actions/deploy-pages`. Set `base` in `vite.config.ts`. Refreshing the data stays a local `npm run harvest` followed by a commit.
- **Pros:** Deploy is deterministic and offline — CI never touches `blomsterlandet.se`, so a deploy can't fail or be rate-limited by the upstream site. The published data is exactly what was reviewed locally. Simplest workflow, fewest moving parts. `harvest/cache/` stays ignored.
- **Cons:** ~3.5 MB of generated data in Git history, growing with each refresh; data freshness is a manual act.
- **Follows:** Nothing existing — greenfield. Mirrors the conventional Vite-on-Pages setup.

### Option B: Keep data out of Git, harvest inside the workflow
- **Concept:** Leave `.gitignore:5` alone. The workflow runs `npm run harvest` (cold, no cache) before `npm run build`, so `public/data/` is materialised only inside the runner. Optionally on a `schedule:` cron to auto-refresh.
- **Pros:** Repo stays lean and generated data never enters history; a scheduled run keeps the site current while the campaign is live.
- **Cons:** Every deploy re-scrapes ~1 740 product pages (~4 min, `claude-opus-5-investigation-blomsterlandet-product-index.md:29`) with a cold cache — deploys become dependent on a third party's availability, markup stability, and tolerance. An upstream layout change turns a routine deploy into a red build. A recurring automated scrape of someone else's site from GitHub's IP ranges is a materially bigger imposition than a local one-off run.
- **Follows:** `harvest/build.ts` unchanged; `--no-cache` path already exists (`package.json:7`).

### Option C: Branch-based deploy (`gh-pages` branch)
- **Concept:** Push `dist/` to a `gh-pages` branch and point Pages at it, rather than using the Actions Pages deployment.
- **Pros:** Works without enabling the Pages Actions source; conceptually simple.
- **Cons:** Commits build output to the repo — the thing Options A and B both avoid. Jekyll processing applies to branch-based sources, requiring a `.nojekyll` marker; the Actions artifact path bypasses Jekyll entirely. Legacy approach with no advantage here.

**Recommendation: Option A.** The two hard blockers are the same under every option, so the differentiator is purely how the data arrives. Option A keeps the deploy hermetic and makes publishing the dataset a deliberate, reviewable act rather than an automated scrape — which matters given the data is harvested from a third party and the campaign it describes expires on a known date. If the site needs to track the campaign automatically, Option B can be layered on later as a separate scheduled workflow that commits refreshed data, without changing the deploy path.

## 9. Open Questions for User

1. **Public or private repo?** Pages from a private repository needs GitHub Pro/Team/Enterprise; from a public one, both the code and the committed dataset become publicly readable. This also decides question 2's stakes.
2. **Is publishing the harvested dataset intended?** The README frames this as *"a local, browsable index"*, and the data is a specification-level copy of Blomsterlandet's live catalogue including hotlinked images from their CDN. Running it locally and republishing it at a public URL are different acts — the second redistributes their content and sends visitor image traffic to their servers. Worth a deliberate yes rather than an implicit one. (Flagging, not blocking — it's your call, and the implementation is identical either way.)
3. **Should the site auto-refresh while the campaign runs?** `meta.json` records the offer ending 11/10; after that the site shows expired prices unless it is re-harvested or retired. Answering this picks Option A alone versus Option A plus a later scheduled refresh.
